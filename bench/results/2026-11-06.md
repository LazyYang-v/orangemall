## ④ 纯落单吞吐（`chain-throughput.sh`）

暂停主消费者 → 5000 用户抢购（1000 单积压在 Kafka）→ 恢复并计时到在途归零 → verify。

| 文件 | 版本 | 耗时 | 吞吐（计时 / 首末成交） | verify |
|---|---|---|---|---|
| chain-throughput-run1 | 12 分区 + 本地事务 | 9.3s | 108 单/s | ✗ 被上一轮残留积压污染（见下） |
| chain-throughput-run2 | 同上（清洁重跑） | 6.6s | 151 / 156 | ✓ |
| run3 / run4 | + Feign OkHttp 连接池 + SKU 本地缓存 | 11.9s（冷）/ 8.0s | 84（冷）/ 126–133 | ✓ |
| run5-batcher | **+ 合并扣减**（冷启动首轮） | 5.9s | 168 / 179 | ✓ |
| run6-batcher | 同上 | 4.3s | **233 / 249** | ✓ |
| run7-batcher | 同上 | 4.2s | **236 / 259** | ✓ |

根因与修复：
1. **单分区串行**：消息 key=activityId，一场活动的所有消息落在同一分区，只有 1 个消费线程在干活 → key 改为 userId，主题 12 分区、12 消费线程。
2. **单分支的 Seata 全局事务**：`createSeckill` 只写订单库，`@GlobalTransactional` 只是平白多了 TC 往返和 undo_log → 改本地事务；地址 Feign 从最多 3 次合并为 1 次。
3. **热点行护航（决定性）**：`profile-drain.sh` 线程快照显示 12 个消费线程中 7 个卡在 `UPDATE seckill_activity SET stock = stock - 1`。
   单独压测该热点行可达 ~600 次/s；但落单时宿主机 CPU 被占满，持锁连接被调度出去，其余线程在行锁上排队。
   → `SeckillDeductBatcher` 合并器：按活动合批，同一本地事务内 `INSERT IGNORE seckill_order` → `stock = stock − k WHERE stock >= k`，
   热点行每批只更新一次；整批不足时回滚并逐条扣减（先到先得语义不变）。
   顺带修复一个潜在缺陷：原来「扣库存」和「写成交记录」是两次自动提交，写成交失败重试会**重复扣 DB 库存**；现在两者同事务，重试由唯一键幂等。
4. OkHttp 连接池 / SKU 缓存 / 去掉日志用的库存 SELECT：在噪声范围内看不出单独收益（run3/run4），保留作为降低每单开销的常规优化。

**run1 污染说明**：上一轮脚本中途报错退出时 EXIT trap 恢复了消费者，其 1000 条积压在本轮 `prepare.sh` 清表/重置库存的同时继续落单，
出现「成交 1024 > 总库存 1000」。Redis 已购集合 = 1000、无重复用户，属压测流程问题而非超卖。
已修复：`prepare.sh` 先恢复消费者并等主题积压与在途归零（静默态）再清理；此后 8 轮 verify（纯落单 6、剖析 1、全链路 1）全部 ✓。
