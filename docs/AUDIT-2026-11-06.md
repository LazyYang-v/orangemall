## ① 最严重的 10 个问题（速览）

完整登记见 §⑤。分级依据 P0=资金风险/安全漏洞、P1=关键权限与核心正确性、P2=架构/测试/可维护性、P3=体验与增强。

### OM-002 【P0·已确认】支付回调可被任何人伪造成功
- **证据**：`mall-gateway/.../AuthGlobalFilter.java:58`（仅拦截 `/api/admin/**`），`POST /api/payments/notify` 匿名可达；合法性只依赖 HMAC 签名，而签名密钥默认值 `orange-mall-sandbox-key-2026` 明文写在 `mall-pay/src/main/resources/application.yml:40` 与 `backend/deploy/docker-compose.yml:19`，且仓库已公开。
- **影响**：任何读者都可读取源码计算合法签名，把任意 PENDING 订单回调成已支付，不付一分钱。
- **修复**：签名密钥环境变量化、去掉默认值（启动 fail-fast）；notify 加渠道侧校验（IP 白名单/秘密回调路径）；仓库只留 `.env.example`。
- **验收**：错误签名/旧 key 回调 → 6003，且正常回调链路回归通过。

### OM-001 【P1·已确认】任何人可为他人的订单创建支付流水
- **证据**：`mall-pay/.../PayService.java:40-54`：`create(userId, orderId, channel)` 拿到 `OrderBrief`（该 DTO 明确含 `userId` 字段，`OrderBrief.java:6`），但从未断言 `brief.userId().equals(userId)`。
- **影响**：登录用户 A 可为用户 B 的订单创建支付流水并支付成功——核心交易链上的越权写。
- **修复**：create/get/notify 三处加 ownership 断言。
- **验收**：集成测试：A 的 token 对 B 订单调 `POST /payments` 返回非本人订单错误。

### OM-003 【P1·已确认】RabbitMQ 消费失败即丢消息，支付成功消息无对账兜底
- **证据**：`AmqpConfig.java:35-42` listenerFactory 默认 AUTO ack + `setDefaultRequeueRejected(false)`，无 DLX 绑定；监听器在 `MqListeners.java:24,35`（关单、支付成功）。抛异常 → 消息直接丢弃。
- **影响**：`close` 丢失有 60s sweep 兜底（`job/Jobs.java`），`pay.success` 丢失则订单停在 PENDING_PAYMENT，无任何对账任务比对 pay↔order 状态。
- **修复**：两队列加 DLX/DLQ+重试；新增对账 job（每 5min：TRADED_SUCCESS 流水 ↔ 非 PAID 订单告警/自愈）。
- **验收**：kill 消费者注入回调，恢复后 5 分钟内订单追平 PAID。

### OM-004 【P1·已确认】JWT 签名密钥默认值入库
- **证据**：`mall-gateway/application.yml:74`、`mall-user/application.yml:57`、`mall-order/application.yml:60` 均为 `secret: ${JWT_SECRET:orange-mall-jwt-secret-2026-change-me}`；compose 注入同一明文（docker-compose.yml:19）。
- **影响**：公开仓库下任何人可自签 `role=ADMIN` token 打进任何暴露部署。
- **修复**：生产强制环境变量、无值拒绝启动；`.env.example` 提供示例。
- **验收**：未注入密钥时网关拒绝启动，错误信息清晰。

### OM-005 【P1·已确认】服务间内部接口 /inner/** 零鉴权
- **证据**：`mall-web-starter/.../ContextFilter.java`（全 36 行）只信任网关透传头；`mall-api` Feign 不携带服务身份；`/inner/**` 可直连（如 `POST /inner/points/change` 修改任意用户积分）。当前唯一屏障是 compose 网络隔离（业务容器未映射主机端口）。
- **修复**：`/inner/**` 增加 service-secret 校验 Filter（网关按服务注入）。
- **验收**：无密钥头直连被拒 401；带正确头正常。

### OM-015 【P1→P2·已确认】后台全文检索走 JSON 提取且无索引（原 OM-006 复核降级）
- **OM-006 复核更正**：细读后撤回「地址越权」定级——普通下单 `OrderService.submit:177-179` 已按 `userClient.addresses(userId)` 过滤；秒杀 `createSeckill:471-477` 同样只在本人地址列表中匹配，他人 addressId 会**静默回落默认地址**，不会写入他人数据。真实问题降为 P3 体验项：无效地址不报错（与 mock 行为一致）。
- **顶替进入 Top10**：`OrderMapper.xml:80-88` admin 按收货人/手机搜索 = `JSON_UNQUOTE(JSON_EXTRACT(address_json,…)) LIKE` + 4 分片 UNION ALL 全表扫，无任何二级索引。数据量增长后是后台最大慢查询来源。
- **修复**：address_json 拆冗余列 `receiver` / `phone`（普通索引），或 MySQL 生成列方案；写迁移脚本。
- **验收**：EXPLAIN 走索引；10 万订单级搜索 <300ms。

### OM-007 【P1·已确认】秒杀 path 签发接口无频控
- **证据**：`SeckillService.issuePath` 每调用执行 Redis SETEX（60s）；nginx `limit_req_zone` 只覆盖 `^/api/seckill/[^/]+/[^/]+/orders$`（POST）；guard 令牌桶只在 submit 生效。
- **影响**：脚本可零成本无限刷 GET path，消耗 Redis 写带宽并在开抢瞬间挤占提交链路。
- **修复**：path 纳入 per-user 令牌桶；nginx 对 path 单独限流区。

### OM-008 【P1·缺失】退款/售后闭环整体不存在
- **证据**：订单状态机止步 COMPLETED；`cancel` 仅 PENDING_PAYMENT（`OrderService.java:303-306`）；payment 表无退款流水域（`01-schema.sql:261-279`，仅回调 TRADE_CLOSED 分支的退款布尔语义）；无后台售后页。
- **修复方向**：refund 域（售后单+退款流水+状态机 WAIT_APPROVAL→REFUNDING→DONE）+ 后台审批页 + 支付渠道模拟退款回调。

### OM-009 【P2·已确认】全仓库零自动化测试
- **证据**：`find backend -type d -name test` 为空；前端无单测；E2E/压测脚本在 /tmp 未入库。
- **修复**：见 §⑭ 测试矩阵（Testcontainers 交易链路为最高性价比起点）。

### OM-010 【P2·已确认】支付回调审计表无限增长
- **证据**：`01-schema.sql:279` `pay_notify_log` 每回调 INSERT（幂等重复也全量入库），无索引、无清理。对比 ops_log 用 Redis List cap 200（`OpsLogger.java:14`）。
- **修复**：created_at 索引 + 保留 30 天清理。

## ⑥ 核心交易链路审查

### 6.1 下单主链（已确认实现，实测有 Seata 回滚证据）

```
checkout ▸ POST /orders/preview（服务端重算：goodsAmount=Σsku.price×n + freight；券 best；points≤余额；签发 submitToken）
        ▸ POST /orders {items, addressId, couponId?, pointsUsed?, submitToken}
        ▸ OrderService.submit（@GlobalTransactional "order-submit"）
             ① Redis DEL submitToken（重复=5001）
             ② 风控：creditScore<300/blocked→5009
             ③ 地址/券/库存预检（5002/4005/2001）
             ④ 服务端重算 calc（防前端篡价），校验积分余额
             ⑤ product.deduct：UPDATE sku SET stock=stock-n WHERE stock>=n
             ⑥ marketing.lock：UNUSED→LOCKED CAS（0 行→异常→全局回滚）
             ⑦ user.changePoints(-pointsUsed)
             ⑧ 插 t_order_{uid&3} + t_order_item_{uid&3}（雪花 id 低 2 位 gene=user_id&3）
             ⑨ 购物车 HDEL（best-effort）
             ⑩ 发 order.delay.30m（TTL 关单）
        ▸ 成功→支付页；失败→Seata 全局回滚（实测：marketing 失败后 product 库存 87→87 原样恢复）
```

遗留小缺口：⑩ 消息发送在事务提交前，若 ⑧ 之后回滚会产生一条「幽灵关单消息」——关单幂等 CAS（仅 PENDING_PAYMENT）保证无害，但属于最终一致性整洁度问题（建议提交后发，属 Phase 1 改动）。

### 6.2 订单状态机

| 迁移 | 触发 | 守卫 | 副作用 | 证据 |
|---|---|---|---|---|
| PENDING_PAYMENT→PAID | MQ pay.success | CAS | 无 | onPaySuccess |
| PENDING_PAYMENT→CLOSED | TTL/DLX、sweep、admin 模拟超时 | CAS | 库存恢复（NORMAL 件）、券释放、积分退回 | close()、Jobs.sweepOverdue |
| PAID→SHIPPED | admin 发货 | 9001 | SF 单号、WS 推送 | ship() |
| SHIPPED→COMPLETED | 用户确认 | 5006 | 券 LOCKED→USED、+payAmount/100 积分、SIGNED | confirm() |
| PAID→用户取消/退款 | — | **不支持** | OM-008 | cancel 仅 PENDING_PAYMENT |
| COMPLETED→售后 | — | **缺失** | OM-008 | — |

### 6.3 竞态与重复场景逐项

| 场景 | 机制 | 结论 |
|---|---|---|
| 重复点击下单 | submitToken Redis DEL-first | ✅（5001 实测） |
| 同一 payment 并发双回调 | CAS UPDATE WHERE status='PENDING' | ✅ 一个胜者，其余 idempotent:true |
| 支付成功 vs TTL 关单 | 双向 CAS（PENDING / PENDING_PAYMENT） | ✅ 互斥胜者；payment 关闭分支退款 flag。待验证：极端延迟对赌 1 次 |
| 回调金额篡改 | amount 相等校验 6004 | ✅ |
| 重复创建支付流水 | 同 order+channel 复用 PENDING + uk_payment_no | ✅（缺归属检查 OM-001） |
| 库存超卖 | 行锁 CAS + Seata 恢复 | ✅ |
| WS 推送失败 | 无 | P3 增强（订单详情轮询兜底已存在） |

集中缺口：消息可靠性（OM-003）、退款闭环（OM-008）、身份与防篡改（OM-001/002/006）——Phase 1 全覆盖。

### 7.1 链路（实测验证）


| Redis/DB 漂移 | 60s 巡检+自动修复 | inflight 滞留挂起 | OM-013 |
| Kafka 重平衡 | 实测 NotCoordinator 重试正常恢复 | 低 | 监控 lag |
| DLT | 预留未接（OM-019） | — | 监控型 handler |
